# 모임원보드 개편 Plan

상태: 1·2·3단계 완료·4단계 준비
상세 기획의 authoritative source: 이 문서
관련 상태: [PROJECT_STATE.md](../PROJECT_STATE.md)

## 전체 작업 순서

1. 모임보드 미리보기 수정
2. 모임보드 내부 내용 수정
3. 동호회 > 모임원 프로필 게시판 수정
4. 모임원 프로필 작성하기 양식 점검

1·2번은 사용자 모바일 실화면 확인으로 완료했고, 3번 모임원 프로필 게시판도 사용자 확정으로 완료했다. 4번은 시작 시 현재 양식을 조사한 뒤 별도로 확정한다.

## 1. 모임보드 미리보기

프로필 보드 안의 “모임 보드” 미리보기 카드를 수정한다. 이 미리보기의 역할은 **앞으로 예정된 나의 모임 참여를 압축해서 보여주는 것**이다.

### 제거·대체 대상 표현

- 가까운 일정 준비하기
- 다가오는 일정 1건
- 단순 특정 날짜 하나 표시
- 하고 싶은 게임 n
- 배우고 싶은 게임 n

### 다가오는 참여

새 구조의 첫 핵심 정보는 “다가오는 참여”다.

예:

- 다가오는 참여 / 9/5(토) · 9/12(토) · 9/19(토)
- 일정이 많아 카드가 길어지면 적정 개수까지만 표시하고 “외 n회”로 축약

내가 실제 참여 예정인 모임 날짜를 기준으로 표시하고, 예정 모임이 전혀 없으면 자연스러운 별도 empty state를 사용한다.

### 다가오는 모임에서의 내 참여 요약

“다가오는 모임” 아래에는 다가오는 모임에서 내가 어떻게 참여할 예정인지 요약한다. 평소 프로필 성향을 다시 넣지 않는다. 원본은 실제 각 모임의 “모임 조율 > 참여자별 상세 > 내 참여자 카드”에 있는 해당 모임 참여 정보다.

현재 데이터 범위에서 사용할 수 있는 예시는 다음과 같다.

- 그 모임에서 원하는 플레이 스타일
- 깊게 / 가볍게 등의 상태
- 초보 환영 여부
- 새 게임 가능 여부
- 게임 유형 관련 선택
- 하고 싶은 게임
- 배우고 싶은 게임
- 모임 한마디

여러 다가오는 모임이 있으면 날짜 표기는 카드 길이에 맞춰 `외 n회`로 축약할 수 있다. 다만 일정별 참여 정보는 첫 일정의 값만 대표로 쓰지 않는다. 참여 스타일 태그, 하고 싶은/배우고 싶은 게임, 한마디는 모든 일정에서 모은 뒤 중복을 제거해 미리보기에 표시한다. 저장 뒤에는 열린 미리보기 카드도 즉시 재조회한다.

개념 예시:

```text
모임 보드 >

다가오는 모임
9/5(토) · 9/12(토) · 9/19(토)

[깊게] [초보 환영] [새 게임 가능]

하고 싶은 게임
아크노바 · 백로성 · 듄 임페리움
```

최종 정보 배치와 길이는 현재 카드 크기 및 모바일 화면을 보고 조정한다. 사용자가 미리보기만 보아도 이 사람이 앞으로 얼마나 자주 나오고, 다가오는 모임에서 어떤 식으로 놀고 싶어 하는지 파악할 수 있어야 한다.

## 2. 실제 모임보드 내부

1번 미리보기 확인 후 구현한다. 현재 2번 구현을 완료했고 PC/모바일 및 상세 진입 검증을 대기한다.

현재 큰 구조인 “다가오는 모임 → 참여 페이스 → 최근 참여” 순서는 유지한다.

### 다가오는 모임

단순 일정 정보가 아니라 각 다가오는 모임의 “모임 조율 > 참여자별 상세” 내 참여자 카드를 그대로 가져오거나 거의 동일한 형식으로 재사용해 나열한다.

상단 액션은 `＋ 참여 등록` 하나만 둔다. 독립 `＋ 하고 싶은 게임`·`＋ 배우고 싶은 게임` 버튼은 두지 않으며, 두 게임 목록은 참여 등록 또는 일정별 수정 과정에서 입력한다. 참여 등록은 기존 플래너 등록 모달을 이 화면 위에서 열고, 일정별 ✎ 수정은 해당 일정의 참여 정보를, × 삭제는 해당 일정의 참여를 각각 처리한다.

일정 카드 헤더는 왼쪽 `날짜 + ✎ + ×`, 오른쪽 `참여 시간`으로 둔다. ✎/×는 기존 플래너의 보조 아이콘·접근성 라벨을 재사용한다. 카드 본문은 값이 있는 참여 스타일·하고 싶은 게임·배우고 싶은 게임·한마디만 표시하고, 개별 빈 항목을 반복 표기하지 않는다. 여러 일정은 카드로 세로 나열하며 일정 전체에 참여 정보가 없을 때만 단일 empty state를 허용한다.

게임 썸네일은 regular 카드 약 24px, compact 플래너 카드 약 16~18px을 기준으로 기존 스타일을 재사용한다.

각 일정 카드에는 가능한 범위에서 다음을 표시한다.

- 날짜
- 참여 시간
- 그날 선택한 참여 스타일
- 하고 싶은 게임
- 배우고 싶은 게임
- 한마디
- 현재 내 참여자 카드에 존재하는 기타 일정용 정보

개념 예시:

```text
다가오는 모임

9/5(토)                     10시~19시
[게임 유형 무관] [깊게]
[초보 환영] [새 게임 가능]
하고 싶은 게임
[아크노바] [백로성]
한마디
초보도 편하게 같이 해요
```

가능하면 새로운 카드 체계를 만들지 않고 모임 조율 참여자별 상세 내 카드의 정보 원천·렌더링·스타일을 재사용한다.

### 참여 페이스

실제 예정 참여는 “다가오는 모임”에서 구체적으로 보여주므로 기존 “참여계획” 명칭은 역할이 겹친다. 이 작업에서 명칭을 “참여 페이스”로 확정한다.

- 실제 예정 일정: 다가오는 모임
- 평소 가능한/희망하는 참여 빈도: 참여 페이스

참여 페이스는 `member_intros`의 기존 데이터를 재사용해 `참여 가능 빈도`, `참여 희망 빈도`, `가능한 요일`, `가능한 시간`을 표시한다. `available_times` 또는 `available_days`의 `flexible`은 기존 포맷터가 자연스러운 유동 가능 문구로 표시한다.

프로필보드는 기존 플레이어 정보 구조를 유지하며 평균 플레이 빈도와 가능한 요일·시간을 계속 표시한다. 참여 가능/희망 빈도는 프로필보드에 추가하지 않고 모임보드 참여 페이스에만 둔다. 가능한 요일·시간을 두 화면에 함께 보여도 같은 `available_days`/`available_times` 원본을 읽을 뿐, 새 필드를 만들거나 의미를 변경하지 않는다.


### 최근 참여

지나간 실제 모임 참여 기록을 보여주는 현재 역할을 유지한다.

최종 역할 구분은 다음과 같다.

- 다가오는 모임: 실제 예정된 내 모임과 각 일정에서의 내 참여 방식
- 참여 페이스: 평소 가능한/희망하는 참여 빈도
- 최근 참여: 지나간 실제 참여 기록

프로필 보드의 “모임보드 미리보기”는 “다가오는 모임” 전체를 한 장에 압축한 요약본이다.

### 모임 조율 최신 확정안

플래너 날짜 카드는 정보를 축소해 별도 화면 진입을 유도하지 않는다. 참여자 정보 아래에 `모임 현황`을 두고, 참여 인원·최대 시간 겹침·선호 유형·겹치는 게임을 충분히 표시한 다음 `모임 조율 ›`로 진입한다.

날짜 전체 화면의 이름은 `날짜 모임 조율`이며, 정보 계층은 다음 순서로 고정한다.

1. `모임 현황` — 현재 모임의 상태 요약. 플래너의 모임 현황과 기본 데이터를 공유할 수 있으나, 화면에서는 제목 밖의 최상위 섹션으로 둔다.
2. `인원 조율` — 실제로 함께 할 게임을 정하는 행동 영역. 현재는 기존 게임 룰렛을 재사용한다.
3. `참여자별 상세` — 평소·오늘·참여 스타일·한마디·하고 싶은 게임·배우고 싶은 게임 등 각 사람의 세부 참여 정보를 한 카드에서 끝까지 보여 준다.

용어는 역할을 혼용하지 않는다: `모임 현황`은 상태, `모임 조율`은 화면 전체 목적, `인원 조율`은 실제 조율 기능, `참여자별 상세`은 사람별 세부 정보다. 참여자 카드에서 같은 정보를 다시 여는 개인 상세 모달은 만들지 않으며, 닉네임/아바타를 통한 프로필 보드 진입은 유지한다.

게임 투표는 현 데이터·API에 표별 선택·사용자별 투표·집계 계약이 없으므로 이번 범위에서 구현하지 않는다. 가짜 UI나 임시 저장 구조를 만들지 않고, 필요한 DB/API 설계와 변경 범위는 별도 Plan·승인 대상으로 남긴다. 복잡한 A/B 그룹, 자동 조 나누기, 그룹 가입/탈퇴도 이번 범위 밖이다.

#### 후속 과제: 인원 조율 실제 기능

- 현재: 기존 게임 룰렛만 재사용한다.
- 추후: 게임 투표 등 실제 조율 기능의 필요성과 사용자 흐름을 검토한다.
- 제약: 게임 투표는 후보·표별 선택·사용자별 중복 방지·집계의 DB/API 설계가 필요하므로, 별도 Plan과 승인 없이는 구현하지 않는다.

## 3. 동호회 > 모임원 프로필 게시판 — 완료

회원 카드는 다른 회원의 **프로필 보드 미리보기 compact 변형**이다. 내 보드 > 프로필 보드 미리보기와 같은 원본·요일/시간 포맷터·정보 순서를 재사용하며, 별도 저장 구조나 API는 만들지 않는다.

- 모바일은 2열 compact 목록이다. 넓은 화면에서만 최소 220px을 보장하는 responsive grid로 열 수를 늘리며, 기존 520px 이상 3열 고정 규칙은 폐기한다.
- 카드 정보 순서는 `아바타 + 닉네임 → 자기소개/한마디(최대 3줄) → 게임 취향 → 평소 플레이 → 가능한 요일·시간 → 좋아하는 게임/해보고 싶은 게임 수 → 프로필 자세히 보기`다. 프로필보드 미리보기와 정보 체계를 갈라놓지 않고, 2열에서는 자연 줄바꿈하는 compact variant로만 조정한다. 작성일은 제거하며 카드 높이는 내용 기반 auto height로 둔다.
- 카드 전체 클릭은 `openOtherProfileSheet(userId)` 하나로 통일한다. 기존 프로필 보드 보기 CTA, 닉네임/아바타와 본문의 분리 클릭 목적지는 제거한다. 본인과 타회원 모두 같은 원칙을 쓰며, 타회원은 기존 읽기전용 내 보드 계약을 유지한다.
- 본인 카드의 수정·삭제·색상 액션은 카드 전체 클릭과 독립 버튼으로 유지하고 이벤트 전파를 막는다.
- 카드 우하단의 작은 `프로필 자세히 보기 ›`는 카드 전체 클릭의 목적지를 알려 주는 affordance이며, 실제 클릭 영역을 그 텍스트로 제한하지 않는다.
- `ccb232ab`의 클릭 분리 과정에서 생긴 닉네임 폭 제한은 새 헤더 구조에서 제거한다. 플래너 참여자 카드의 모임 보드 계열 동선은 이 작업의 예외이며 바꾸지 않는다.

## 4. 모임원 프로필 작성하기 양식

이후 순차 진행한다. 현재 상세 설계를 임의로 추가하지 않는다.

## 구현 원칙

- 기존 데이터·API·렌더링 구조를 최대한 재사용한다.
- 모임 조율의 “참여자별 상세 내 카드”와 모임보드의 다가오는 모임 카드는 가능한 한 같은 정보 원천과 UI 구조를 공유한다.
- DB 스키마, 저장 형식, API 계약 변경이 필요하면 임의로 변경하지 않고 Plan/사용자 승인 대상으로 먼저 보고한다.
- 이 문서의 확정 기획을 임의로 다른 의미로 재구성하지 않는다.
