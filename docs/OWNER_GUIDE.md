# 코티지 홈페이지 구조를 쉽게 이해하기

이 문서는 코티지 홈페이지의 **소유자용 안내판**이다. 코드를 고치기 위한 기술 정본이 아니라, "왜 이 수정이 필요한가?"와 "어디까지가 공통 구조인가?"를 쉽게 이해하도록 돕는다.

정확한 기술 규칙은 이 문서가 아니라 링크된 정본 문서에서 확인한다.

## 내가 알아야 하는 수준

소유자는 아래 정도만 알면 충분하다.

- 화면마다 관리하는 주인이 있을 수 있다.
- 새 화면은 나를 연 화면의 바로 위에 떠야 한다.
- 사람 자체와 화면에 보이는 이름은 다르다.
- 여러 곳에서 같은 문제가 보이면 공통 구조부터 고쳐야 한다.
- 한 화면만 보이게 하려고 임시 숫자나 예외를 붙이는 일은 경계한다.
- 누가 화면을 열고, 닫고, 기록하는지 정해져 있어야 한다.

반대로 아래는 몰라도 된다.

- 함수명, 파일명, 실제 z-index 숫자
- HTML 구조나 portal 같은 구현 방법
- 화면 번호표(token)의 내부 형식
- SQL, 조회문, 이름 연결 코드의 세부

수정 보고를 받을 때 "이 변경이 어떤 주인과 어떤 공통 원칙을 지키는가?"를 판단할 수 있으면 충분하다.

## 1. 화면에도 주인이 있다

홈페이지에서 화면이 열릴 때는 크게 두 종류가 있다.

- **Host**: 여러 화면을 담아 순서와 바깥틀을 관리하는 무대 관리자다.
- **기능 화면(local surface)**: 프로필, 모임, 게임처럼 자기 안의 열기·닫기·뒤로가기를 직접 관리하는 화면이다.

현재 Host가 직접 자식 화면으로 관리하는 것은 추천 게임 전체보기(`recommend-all`)다. 반면 프로필, 모임 조율, 게임 정보·위치·안내는 이미 자기 기능이 관리하는 화면이다.

모든 화면을 Host 자식으로 만들면 쉬워 보일 수 있지만, 기존의 뒤로가기, 닫기, 스크롤, 작은 화면 모양이 달라질 수 있다. 그래서 이미 잘 관리되는 기능은 자기 흐름을 유지한다.

작업할 때 주의: "모달처럼 보인다"는 이유만으로 Host 화면으로 바꾸지 않는다. 먼저 그 화면의 원래 주인이 누구인지 확인한다.

자세한 기술 정본 → [UI_STRUCTURE.md](UI_STRUCTURE.md), [UI_PATTERNS.md](UI_PATTERNS.md)

## 2. 새 화면은 부모 바로 위에 뜬다

화면은 종이 여러 장을 포개는 것과 비슷하다. 새 종이는 자신을 꺼낸 종이 바로 위에 놓여야 한다.

그래서 새 화면마다 `9000`, `9500`처럼 큰 숫자를 새로 정해 올리는 대신, **나를 연 Host 또는 부모 화면의 바로 위 층**을 받아 사용한다. 이를 "부모 기준으로 위에 뜬다"고 생각하면 된다.

이 방식이면 부모가 더 높은 층에 있어도 자식이 뒤로 숨지 않는다. 반대로 "안 보이니 9999" 같은 임시 처방은 다른 화면을 덮거나 나중에 또 같은 문제를 만든다.

작업할 때 주의: 보이는 순서 문제가 생기면 숫자부터 올리지 말고, 어떤 화면이 요청했고 어느 층을 받아야 하는지 먼저 확인한다.

자세한 기술 정본 → [UI_PATTERNS.md](UI_PATTERNS.md) P3-A, P3-B

## 3. 프로필 안의 화면은 프로필 안에서 움직인다

내 보드나 회원 보드에서 프로필 보드, 모임 보드, 기록 보드 등을 열 수 있다. 이것은 건물을 새로 짓는 일이 아니라, 같은 프로필 안에서 한 방 더 들어가는 것에 가깝다.

하위 화면이 열리면 원래 프로필은 잠시 뒤에 보관되고, `←`나 ESC를 누르면 다시 돌아온다. 하위 화면을 새 Host 화면으로 바꾸지 않는 이유는 이 자연스러운 "한 단계 돌아가기"를 지키기 위해서다.

작업할 때 주의: 프로필 안의 보드에서 문제가 생겼다면 새 화면을 추가하기보다, 프로필의 local navigation 규칙을 먼저 본다.

자세한 기술 정본 → [UI_PATTERNS.md](UI_PATTERNS.md) P6

## 4. 사람의 이름과 사람 자체는 다르다

사람을 구별하는 기준은 **stable user_id**다. 학교로 비유하면 학생번호다. 닉네임은 학교에서 부르는 별명이다.

별명은 바뀌거나 비슷할 수 있으므로, 통계·업적·참여 횟수처럼 "누구의 것인가"가 중요한 정보는 학생번호처럼 변하지 않는 ID를 기준으로 본다.

다만 모임원 공개 프로필에서는 `member_intros.nickname`이 그 사람이 공개적으로 보여 주는 이름의 기준이다. 즉, 사람을 찾을 때는 ID를 쓰고, 사람에게 보여 줄 이름은 공개 닉네임을 쓴다.

작업할 때 주의: 이름이 같거나 비슷하다는 이유만으로 같은 사람이라고 처리하지 않는다.

자세한 기술 정본 → [js-api.md](js-api.md)의 stable identity / public nickname 계약

## 5. 옛 기록의 이름은 안전하게 연결한다

옛 플레이 기록에는 ID 대신 `덕 지`, `덕지`, `서은희`처럼 이름 글자만 남아 있을 수 있다. 이런 기록을 현재 회원과 연결하는 도우미가 있다.

이 도우미는 이름이 정확히 맞고, 한 사람으로 확실히 정해질 때만 연결한다.

- 띄어쓰기처럼 정해진 방식으로 정리한 뒤 정확히 비교한다.
- 일부 글자만 같다고 연결하지 않는다.
- 같은 이름 후보가 둘 이상이면 자동으로 고르지 않는다.
- 현재 데이터에 ID가 있으면 옛 이름이 ID를 대신하지 않는다.

원래 기록의 글자도 억지로 바꾸지 않는다. 연결은 표시·집계할 때만 안전하게 한다.

자세한 기술 정본 → [js-api.md](js-api.md)의 participant resolver 계약

## 6. 화면을 연 쪽이 자기 화면을 관리한다

화면을 열 때는 번호표 하나를 붙인다고 생각하면 된다. A가 연 화면에는 A의 번호표가 붙고, 닫을 때도 같은 번호표를 가진 요청만 그 화면을 닫을 수 있다.

이 규칙은 늦게 도착한 닫기 요청이나 이미 끝난 화면의 요청이, 지금 보고 있는 다른 화면을 잘못 닫는 일을 막는다. 화면을 연 쪽이 열림과 닫힘의 책임을 함께 가진다.

자세한 기술 정본 → [js-api.md](js-api.md)의 `COTTAGE_ACTIVE_VIEWS`, [PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md)의 이용시간 추적 흐름

## 7. iframe 안의 기록은 한 곳에서만 한다

iframe은 페이지 안에 들어가는 작은 페이지다. 부모 화면과 iframe이 둘 다 체류시간을 기록하면 출석을 두 번 적는 것과 같다.

그래서 iframe 안에 들어간 페이지는 기록의 주인이 아니다. 부모 화면이 한 번 열었을 때 기록을 시작하고, 닫을 때 한 번 끝낸다. iframe은 필요한 상태만 부모에게 알려 준다.

자세한 기술 정본 → [js-api.md](js-api.md), [PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md) §6

## 8. iframe은 자신이 안에 들어왔다는 사실을 잃지 않는다

같은 페이지라도 직접 열면 보통 페이지이고, 다른 화면 안에 들어가면 embed 화면이다. embed 화면에서는 중복되는 큰 헤더나 소개 영역을 숨기고 실제 기능만 보여 준다.

주소의 일부가 이동 과정에서 사라지는 경우에도, iframe은 query와 hash 표시를 함께 읽어 "나는 embed 화면"이라는 사실을 최대한 유지한다.

자세한 기술 정본 → [PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md)의 embed 모드

## 버그 수정 보고를 읽는 법

에이전트가 "고쳤다"고 보고하면 아래를 물어보면 된다.

1. 증상만 가렸나요, 여러 화면에 공통인 원인을 고쳤나요?
2. 특정 사람 이름이나 특정 화면만 따로 적어 넣었나요?
3. 이미 있는 공통 도우미와 규칙을 사용했나요?
4. 사람 ID, 화면 주인, 부모·자식 관계를 그대로 지켰나요?
5. 같은 문제가 다른 곳에도 생길 수 있다면 함께 확인했나요?
6. 새로운 오래가는 규칙이 생겼다면 기술 정본 문서에 짧게 기록했나요?

답이 "특정 화면만 급히 보이게 했다"에 가깝다면, 한 번 더 공통 구조를 확인하는 편이 안전하다.
