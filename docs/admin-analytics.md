## 1. 원칙

2026-07-19 사용자 요청("유효 데이터들이 더 직접적이고 유기적으로 드러났으면. 페이지별로도, 페이지 내 항목별로도")에서 도출. **근거는 관념이 아니라 이 화면에서 실제로 터진 발견 #1~#14다** — 그 14건 중 "지표가 부족하다"는 하나도 없었고 **전부 "이 숫자가 무엇을 센 것인가"의 문제**였다.

⚠️ **이건 시각 디자인 규칙이 아니다.** `DESIGN_RULES.md`(팔레트·모바일·`border-radius`·sticky)와 범주가 다르다. ①②는 **데이터 정의**, ③④⑤는 **정보 구조(IA)**다.

### ① 모든 수치는 "무엇을·언제·누구를" 셌는지 달고 다닌다

단위(회/명)·기간·모집단을 표기하거나, 표기가 지저분하면 **화면 전체가 하나의 기준을 따르게** 한다.

- 위반 실례: **#9**(요약 카드 5장의 기간이 오늘/7일/30일/누적으로 제각각인데 1장만 표기) · **#11**("7일" 버튼이 실제로는 이번 주) · **#5**(필터 칩은 누적 341, 목록은 그날 4명)
- **판정법**: 화면의 숫자 하나를 짚고 "이건 언제, 누구를 센 거냐"에 답할 수 없으면 위반.

### ② 절대수보다 분모 붙은 수 — 단, 분모는 같은 기간·같은 모집단

"23명"은 많은지 적은지 알 수 없다. "그 기간 방문 249명 중 23명(9%)"이면 즉시 판단된다.

- ⚠️ **분모를 붙이기 전에 분자가 분모에 포함되는지 실측**한다. 2026-07-19 도달률 설계 시 `page_events`의 고유 `session_key` 70개가 `page_sessions`에도 **100% 존재**함을 확인하고서야 지표를 인정했다. 교집합이 100%가 아니면 그 비율은 거짓말이 된다.
- ⚠️ **기간을 맞춘다.** 전체 방문자 763명이 아니라 **이벤트가 존재하는 기간의 249명**이 분모다.
- ⚠️ **섞으면 안 되는 모집단은 나눈다.** 도달률이 회원 88%(16명 중 14명) vs 비회원 24%(233명 중 56명)로 갈린다 — 합친 28%는 두 이야기를 다 지운다.

### ③ 파생 가능한 값은 그 자리에서 반복하지 않는다

`평균 = 회 ÷ 명`은 이미 있는 두 수에서 나온다. 좁은 카드에 셋을 넣으면 셋 다 안 읽힌다.

- **단, 비교가 목적인 자리에선 파생값이 1급이 된다** — 이벤트 탭의 단계별 평균은 단계 간 몰입도 비교라 유지한다.
- **판단 기준**: "이 수가 없으면 못 하는 판단이 있는가?" 없으면 빼라.
- 적용 실례: 2026-07-19 "요약 카드에도 평균을 넣을까?"는 이 원칙으로 **기각**, 같은 날 "도달률을 넣을까?"는 ②에 해당해 **채택**.

### ④ 한 화면은 한 질문에 답한다

요약=**어디가** 활발한가 / 방문=**언제** 오나 / 유입=**어디서** 오나 / 페이지=**무엇을 보나** / 이벤트=**무엇을 하나** / 회원=**누가**.

- 위반 실례: **#12**(회원 탭에 「회원별 이용시간」이라는 *기간 집계* 차트가 있다 — 방문 탭 소관)
- 날짜 네비가 어느 탭에 붙느냐도 이 원칙으로 결정된다(**#5·#6**: 회원=명부라 기간 무관, 이벤트=기간별 건수가 본질).

### ⑤ 지표에서 그것을 구성하는 다음 단위로 내려갈 수 있다 (드릴다운)

**"유기적"의 정체가 이것이다.** 한 숫자를 보고 "이걸 만든 게 누구/무엇이지?"로 내려가는 길이 있어야 한다.

- 있음: 요약 카드 → 해당 탭(`data-nav-tab`) · 회원 카드 → 그 사람의 페이지 분포(2026-07-19 B단계)
- **없음(최대 결손)**: 이벤트 계열 → 그 계열의 단계 / 페이지·이벤트 → **그걸 한 사람들** / 페이지 → 그 페이지를 본 회원 목록
- 지금은 **각 탭이 섬**이라 "이 숫자를 만든 사람이 누구지?"에서 막힌다. 하나씩 고쳐서는 안 메워지는 종류의 결손.

## 2. 화면 구조

| 탭 | 답하는 질문 | 날짜 네비 | 비고 |
|---|---|---|---|
| 요약 | 어디가 활발한가 | ✅ | 카드 5장, 클릭 시 해당 탭으로(`data-nav-tab`) |
| 방문 | 언제 오나 | ✅ | 날짜별 차트 + 서브탭(시간대/회원·비회원). **요일·재방문율은 `disabled title="준비 중"`** = 2단계가 붙을 예약석 |
| 유입 | 어디서 오나 | ✅ | 유입경로별 + 유입×페이지 교차 |
| 페이지 | 무엇을 보나 | ✅ | 가로막대(막대=횟수, 막대 위 텍스트=체류 → **#8**) |
| 이벤트 | 무엇을 하나 | ✅ | 퍼널 3계열. 전환율은 **사람 집합 교집합** 기준 |
| 회원 | 누가 | ❌(의도) | 명부. 카드마다 `📄 페이지 N개` 펼침 |

**이벤트 계열 표(`EVENT_FAMILIES`)가 단일 출처다.** 조회 목록(`EVENT_ALL_TYPES`)이 여기서 파생되므로 **새 `trackEvent` 타입은 반드시 여기 등록**한다. 안 하면 관리자 화면이 아예 조회하지 않아 조용히 안 보인다(그래서 실제로 77%가 안 보였다 = **#13**).

## 3. 데이터 소스와 함정 (읽기 전 필독)

| 소스 | 용도 | 함정 |
|---|---|---|
| `page_sessions` | 방문·체류·페이지 분포 | 11,500행+. `duration_sec=0`이 14.7%(heartbeat 전 이탈) |
| `page_views` | `__visitor__` 마커 = 방문 명/회 | legacy 행 70%가 `session_key` NULL(소급 불가) |
| `page_events` | 이벤트·퍼널 | `session_key` **2026-07부터 100%, 06월은 8%** |
| `anon_sessions` | 비로그인 heartbeat | `today_date`가 세션 시작값 고정(자정 넘김 버그) |

- 🚨 **관리자(`4916417947`)는 트래킹에서 영구 제외**된다(`_shouldSkipAnalytics`). **이벤트 기반 지표는 관리자 활동을 절대 반영하지 않는다** — "왜 내 활동이 없지?"가 아니라 설계된 동작.
- 🚨 **PostgREST `max-rows`는 대시보드 설정이라 마이그레이션에 안 남는다.** 현재 50000(2026-07-18 상향). DB 재구축 시 1000으로 돌아가 **조용히 91% 절단이 재발**한다. 상세는 [db-schema.md](db-schema.md) "PostgREST max-rows".
- 🚨 **`page_sessions.page`는 슬러그가 아니라 표시 라벨을 저장한다**(#14) — 라벨을 바꾸면 과거 데이터가 쪼개진다.
- 🚨 **"방문자 N명"의 소스가 둘이고 서로 호환되지 않는다** (2026-07-19 P1에서 실측 확정):
  - **비율의 분모로는 `page_sessions`만 쓴다.** 이벤트를 일으킨 회원 14명 중 `__visitor__`에 있는 사람은 **9명(64%)**뿐 — 분자가 분모 밖으로 새서 **100% 초과가 나온다**(#10과 같은 종류의 거짓말). `page_sessions`는 회원·비회원 모두 **100% 포함**(7일/30일/전체 전부).
  - `__visitor__`(방문 탭 차트·유입·도넛)와 `page_sessions`(도달률)는 **숫자가 다른 게 정상**이다. 원칙 ①에 따라 **어느 기준인지 화면에 표기**해서 공존시킨다(도달률 줄의 "방문=세션 기록 기준").
  - 두 소스를 통일하는 건 방문 탭 전체가 `__visitor__` 기준이라 **Red 규모** — 지금 손대지 말 것.
- **행 수 자체가 거짓말한다**: 정확히 `1000`이면 절단, `0`이면 RLS를 의심. 둘 다 `error`가 `null`이라 감지기에 안 걸린다. 상세는 CLAUDE.md 「DB 함수 에러 처리」.

**검증 하니스**: `scripts/audit-admin-analytics.js`(DB층 — 절단/RLS) · `scripts/shot-admin-tabs.js`(표시층 — 6탭 스크린샷 + #5·#6·#7 자동 판정, 전환율 100% 초과 회귀 가드).
⚠️ **하니스 출력 폴더를 리포 안으로 주지 말 것** — Live Server가 리포를 감시해 PNG 쓰기가 페이지 리로드를 유발하고, 두 번째 탭부터 죽는다(원인 규명에 2회 실패를 소모했다).

### 🔬 방문/이용 집계 정확도 (별도 계열)

- ① **`duration_sec=0`이 14.7%** — heartbeat(1분) 전 이탈. 관리자 분석에서 시간 미표시. 표시 조건이 `todayS > 0`이라 **0이면 항목이 DOM에서 빠진다**(0으로 표시되는 게 아님).
- ② **과거 `session_key` NULL 70%** — 007 이전 legacy, **소급 불가**. 대상 아님.
- ③ **이용시간 기기 중복** — 다기기 동시 사용 시 합산. 해법 방향은 서버 세션 단위 관리(Red).
- ④ **`_startAnonHeartbeat` 자정 넘김 버그** — 1분 인터벌이 `today_seconds`만 갱신하고 `today_date`는 세션 시작값 고정. `page_sessions` 파생값을 우선 쓰므로 그 행이 없을 때만 발현.
- ⑤ **가상 페이지 키↔라벨 정합성** — 새 `_trackPvOnce` 키 추가 시 `page-labels.js` 동시 갱신 필요(안 하면 slug 노출, 조용히 발생).
- ⑥ **로그인 시 잔여 누적시간이 `page_sessions`에 안 들어감** — INSERT 경로가 `visibilitychange` 하나뿐. `beforeunload`/`pagehide`는 localStorage만 갱신. 설계는 `git show 4838691^:docs/PLAN_page_sessions_on_login.md`로 복원 가능.

**성격**: 대부분 "추적 로직 설계"(heartbeat 타이밍·기기 단위 세션) 문제라 Red + Plan. 코드 리팩토링보다 **집계 모델 재설계**에 가깝다.

## 6. 재조사 금지 — 기각된 가설

「관리자 금일이용데이터 간헐 미표시」 추적에서 **근거를 갖고 기각**된 것들. 다시 파지 말 것.

- ⓐ **로드순서 레이스** → 스크립트가 전부 classic이고 인라인 IIFE가 `supabase-client.js` 뒤라 `window.CottageDB`는 항상 정의됨.
- ⓑ **`tried` 래치 + 1200ms 게이트** → `isOwner()`가 동기 localStorage 읽기라 그 시점에 확정됨.
- ⓒ **KST 타임존 불일치** → 읽기/쓰기가 전부 동일 공식(`Date.now()+9h`).
- ⓓ **"조회 실패가 조용히 빈 값"** → 감지기 1~4단계가 켜진 상태에서 콘솔 대괄호 라벨 에러 **0건**.

**단일버그 추적은 2026-07-18에 종료되고 페이지 전체 감사로 대체됐다.** 남은 유력 후보는 ③ 에러 수집 부재(=`console.error`가 우리에게 안 옴)와 위 ①`duration_sec=0`.
